# Maintenance integration: merge checklist

**Not ready to merge.** The normal process model is implemented, but the full
compatibility and failure audit is still open. The version remains 1.11.3;
the version bump belongs in a separate PR.

For operators, read [Maintenance without another service](MAINTENANCE_INTEGRATION_UX.md).
For test details and commands, read the [evidence appendix](MAINTENANCE_INTEGRATION_EVIDENCE.md).

## Experience that must remain simple

Keep using the existing server command, maintenance commands and GC timer.
Normal tracking runs inside their existing process. It adds no service, port,
mount, schedule or operator-selected task ID. Every scheduled invocation starts
fresh work; saved history never replaces a new scan.

The optional `shardline maintenance ...` runner can use a child for deadlines
and CPU limits. Those controls do not apply to ordinary commands.

Tracking must preserve command output, exit codes, configuration handling,
diagnostic exports and existing safety barriers. Failure to save optional
history produces a warning, not a verified completion or an automatic retry.

## What has been tested

These are scoped results, not a claim that every deployment is compatible:

- Released/current server startup, restart, publication and rollback fixtures
  preserve domain data, released migration records and existing runtime grants.
  Current startup and writes also pass before the optional owner upgrade,
  without new tracker payload objects. Ordinary startup introduces no worker service.
  Native admin checks distinguish readiness from unavailable history before the
  owner upgrade, then select shared history after upgrade and process restart.
  Optimized mixed-node overlap and rollback pass before and after the usual
  owner setup. Read-only container commands preserve released output without
  writable root or temporary storage; upgraded history needs no S3 write grant.
- Public-library local router startup covers all three server roles with an
  existing application logging subscriber. Consecutive startups sweep newly
  expired legacy LFS sessions and save distinct completed runs in existing metadata.
- A forced deny policy on the optional Postgres history table blocks both reads
  and writes through an already-open store. Startup still sweeps expired LFS
  sessions; history inspection warns when new metadata history is unavailable.
  A real-Postgres schema-routing fixture verifies distinct login schemas,
  immutable binding to the actual work session, no replacement after session
  loss, and restricted-router fallback without new task payload objects.
- The unchanged GC service generated by released 1.11.3 runs in a Debian guest
  with its original systemd restrictions after replacing the binary.
  Optimized native reboots before mutation and after mutation/report creation
  preserve exact saved records and leave interrupted local GC unresolved.
  No scan is replayed; an explicit fresh invocation discovers new work.
- Ordinary maintenance keeps its original PID, output and handlers. Fixtures
  cover read-only roots, fresh runs, contention and loss of database ownership.
  Private-state and receipt faults preserve results; tracking warnings use stderr.
  Optimized two-machine drills cover node partition/loss plus connection loss
  during rebuild, repair and GC mark. Independent contenders complete after
  ownership releases; lost work is not promoted to completion or replayed.
  An optimized container-replacement drill also preserves interrupted evidence,
  completes fresh startup work, confirms one server PID, and exits normally on
  SIGTERM before another fresh startup.
- Local and S3 copies preserve payload bytes, counts and released rollback.
  Their tracker does not write control objects into payload inventory or require
  source write access. S3-only destination history is temporary and host-local.
  An actual automatic SQLite history fixture also preserves released fsck
  output and source evidence bytes through a released payload-only copy.
  Optimized local maintenance passes under a 0555 root with existing writable
  metadata, and a retention-only Postgres account preserves its existing grants.
- Covered PostgreSQL writes reject lost ownership. Covered writes to an object
  with an unresolved remote delete return a retryable error. Verified saved
  replies can settle the matching delete without sending another user delete.
  Seven optimized real-Postgres/MinIO fault drills cover lost acknowledgements,
  delayed deletes, restricted GC accounts, denied receipt writes, and recovery
  by ordinary repair or a fresh sweep after a database outage. Unrecorded GC
  outcomes stay unresolved even after their saved delete replies settle.
  All 21 Postgres delete-guard tests pass with a configured real database,
  covering direct file, dedupe, reconstruction and stored-object references,
  rejected-publication rollback, restricted accounts, cross-schema settlement,
  stale attempts and publication/deletion races.
- Postgres file-reference copy and deletion keep an existing request ownership
  connection, including with a one-connection pool. A real database fixture
  verifies successful copy and both delete modes, no publication after owner
  termination, preservation of the source, and fresh retry. Expected-hash
  cleanup also preserves a concurrent winner after waiting on its row lock.
  Ordinary guarded reads retain their read pool to avoid ownership-mutex
  re-entry. All seven publication fixtures pass; the corrected optimized binary
  passes the 11 selected deployment drills and restricted OCI/S3 process drill.
  These results cover the named paths, not every lower-level library caller.
- Newly staged Postgres uploads check their backing bytes inside the publication
  transaction. A configured database fixture deletes an actual staged xorb,
  settles its marker, and verifies rollback of file and S3 metadata, a retryable
  response, successful fresh retry, unchanged failed preconditions and lock
  lifetime. It uses local CAS for the deterministic interleaving; this does not
  establish the behavior of arbitrary legacy records or unguarded deletion.
- Native Postgres shard publication also checks physical xorbs and normalized
  shard bodies inside its existing transaction. A real native-payload fixture
  verifies pending rejection, post-settlement byte loss, rollback of file and
  dedupe rows, actionable retry errors, successful retry through the ordinary
  handler and a matching download. Its local-CAS payload store does not prove
  remote-S3 faults or storage presence for lower-level metadata-only callers.
- Covered PostgreSQL publication rejects a Repeatable Read or Serializable
  snapshot that predates delete admission. Real database fixtures verify no
  visible publication, retryable HTTP/OCI/S3 responses, successful fresh retries
  without changing isolation, and consistent snapshot/physical lock ordering.
  Long transactions at these isolation levels can delay unrelated delete
  admissions; broader concurrency and cost still need assessment.
  The optimized snapshot-protection revision also passes all 11 selected
  deployment drills, the restricted released/current OCI/S3 process drill and
  184 configured PostgreSQL index tests. These extend the evidence above; they
  do not close the broader merge gates below.
- History distinguishes completed, failed and unresolved runs. Signed records
  and reports are verified; unfinished and corrupt evidence is retained.
  Optional archive cleanup now observes server shutdown and router lifetime,
  with tests for stopping inventory scans and resuming partial evidence retirement.
  Its stop signal does not cancel application jobs or ordinary CLI commands;
  storage I/O already in progress can finish. The final optimized CLI also passes
  the restricted released/current OCI/S3 process drill with no server children.
- Public-router HTTP tests follow history cursors without dropping corrupt
  entries, reject unsupported filters, and preserve an explicit recording warning
  on an empty history response while readiness remains ready. These local fixtures
  distinguish history availability from application readiness; they do not prove
  every deployment layout.
- A mark-only GC comparison preserves released output, status and payload bytes
  with 4,096 synthetic orphan entries. Both diagnostic exports exceed 1 MiB;
  all entries and persisted timestamps match. This does not establish reclamation
  safety or production performance.
- Optimized released/current binaries pass the repository's local full benchmark
  matrix at concurrency 1, 32 and 128. Report schema and non-performance counters
  match. Both binaries' fsck reads the nine current-generated stores with matching
  output; current maintenance records completion separately from payload data.
  This measures the existing workload, not distributed capacity or history scaling.
- An explicit optimized SQLite fixture fills all 4,096 automatic history slots
  with real completed, unfinished and unreadable histories. Pagination and
  oldest-first cleanup preserve unresolved evidence and user payload bytes.
  The slowest cleanup call was 0.802 seconds in this local fixture; this does
  not establish deployment latency or the cost of larger legacy histories.
- An explicit optimized PostgreSQL fixture also fills all 4,096 automatic
  history slots, rejects further admission, paginates every ID, preserves
  interrupted/corrupt evidence and user payload, and records fresh work after
  cleanup. Full inspection took 37.073 seconds; the slowest cleanup call took
  5.961 seconds in the disposable database. This establishes the tested logical
  capacity behavior while leaving deployment latency and larger archives open.
  After batching verified blob/report reads, a clean rerun completed full
  inspection in 35.159 seconds, with a slowest cleanup call of 4.538 seconds.
  Safety assertions still passed; these fixture measurements are not deployment
  latency bounds.
  Batching retirement deletion subsequently passed the same capacity fixture:
  full inspection took 33.903 seconds, total cleanup 210.186 seconds and the
  slowest cleanup call 4.180 seconds. Separate configured fixtures cover
  second-batch failure and recovery, caller rollback and existing role permissions.

## Known gaps

The following still need implementation or stronger evidence before merge:

- **Remaining write paths and older GC.** Some library callers and references
  hidden inside legacy payloads do not use the covered ownership checks.
  Direct Postgres file, dedupe, reconstruction and stored-object reference
  publication is covered; this gap concerns paths outside those boundaries
  and references not visible in the protected metadata.
  In particular, lower-level `PostgresRecordStore` methods publish metadata
  without inspecting object storage. The plain `commit_native_shard_metadata`
  entry point also supplies no caller-derived physical reference keys; the
  server uses the connection-bound variant with those keys and checks backing
  bytes in its publication transaction. Database reference protection alone
  does not prove storage presence for library callers.
  The metadata-only API also exists in released 1.11.3: its native commit writes
  records and mappings in a database transaction without an object-store input.
  This is an existing guarantee boundary, not evidence that the integration
  introduced missing-content publication. It still limits the stronger guarantee
  this branch can promise to library users.
  An older GC binary does not establish the current remote-delete markers.
- **Uncertain remote outcomes.** Missing or invalid delete replies leave an
  object blocked. Object absence alone cannot safely clear it. Recovery and
  remote effects outside the covered paths need further checks.
- **Scale and retained history.** Bounded pages are tested; whole-operation cost,
  larger reports, broad deployment performance and total unresolved-history
  growth are not fully established. Automatic private-workspace admission is
  limited to 4,096 slots, preserving evidence and falling back to shared history;
  active private workspaces and retired scratch now share that limit. Shared
  metadata has its own 4,096-run automatic-admission budget, with new artifacts
  limited to 64 KiB. Existing evidence and explicit legacy imports remain
  unrestricted. These are logical admission limits, not physical disk limits;
  whole-operation cost and broader scaling remain open.
  Metadata fixtures with 132, 1,026 and 4,096 runs
  drain completed history in batches while retaining unfinished and corrupt history, but
  retention and legacy inspection still walk the inventory. Metadata inspection
  stops after its eligible page is settled, but filtering unrelated history can
  still require a longer scan; bounded output does not bound latency.
- **Remaining deployment layouts.** Work-specific database/schema routing,
  row policies, narrower accounts, library embedding and legacy history need
  coverage beyond the passing fixtures. Corrupt, unfinished or unrelated legacy
  objects can still enter an older raw storage copy.

## Eight merge gates

All eight remain the completion criteria. No gate is closed by a dependency
upgrade, a test count or the optional runner alone.

1. Unmodified server commands and manifests initialize tracking automatically.
   Cover local metadata, Postgres/S3, server roles and library embedding without
   an operator-managed daemon or new mount.
2. Preserve stdout/stderr, exit codes, configuration handling, diagnostics exports
   and safety barriers. Run the released GC service with its existing restrictions.
3. Consecutive schedules execute fresh scans. Concurrent invocations have defined
   ownership; completed history is never reused as a fresh reachability snapshot.
4. Large, long-running operations retain supported behavior. Budgets, report
   handling, retention and cleanup cause no undocumented limits or unbounded growth.
5. Interrupt controllers and workers at admission, checkpoint, external mutation,
   report proposal and completion acknowledgement. Recovery cannot falsely report
   completion, repeat an unknown mutation or permit an ownerless stale writer.
6. Test shutdown, reboot, container replacement, cross-host replacement and
   competing shared owners. Include coordination-connection loss while the old
   process remains alive. Specify what may continue and what must reconcile.
7. Mixed old/new nodes and rollback preserve history, domain formats and metadata
   arbitration. New records must not make old binaries misinterpret domain state.
8. Operators distinguish server readiness, failed optional jobs and maintenance
   needing reconciliation without understanding dependency internals.

## Ownership and recovery rules

Task history records an outcome. Transactions, locks and operation-specific
fencing authorize changes. A separate PID does not provide exactly-once effects.
A foreign PID does not prove that a remote job is alive or dead.

An idempotency key protects a retry when the duplicate check and effect commit
together. A fence protects takeover when the effect atomically rejects an old
owner. Unknown effects require investigation before retry; a new task ID does
not make a retry safe. Recorded completion does not certify current cluster health.

Keep existing request, upload, cache, OIDC and webhook owners. Starting Shardline
must not turn these into automatically retried maintenance jobs. Preserve lazy
Hub secret upgrades when a startup sweep fails.

The normal owner-run database upgrade installs the optional metadata and
protection functions. See [rolling upgrades](ROLLING_UPGRADE.md) for deployment
steps and limitations; the tracker itself requires no new service or runtime grant.
